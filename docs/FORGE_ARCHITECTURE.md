# FlowLens — Forge Architecture

**Authority:** Level 2 — Technical Architecture  
**Parent:** `docs/PROJECT_OVERVIEW.md`  
**Status:** Inspection exports, v1/v2 import, visualization, issue flow storage and user preferences implemented.

## 1. Purpose

Describe how FlowLens is structured as a single Atlassian Forge application.

This document defines component responsibilities, integration boundaries, data management, and important technical decisions.

It must remain aligned with the product requirements defined in `PROJECT_OVERVIEW.md`.

## 2. Application Architecture

FlowLens is one Forge application integrated into Jira Cloud.

It uses a Custom UI issue panel and a Forge resolver.

```text
Jira Cloud
    │
    └── FlowLens Issue Panel
            │
            ├── React Custom UI
            │      ├── Jira context
            │      ├── Inspection prompt
            │      ├── Import/export
            │      └── Flow visualization
            │
            └── Forge Resolver
                   ├── Application operations
                   ├── JSON validation
                   ├── Flow management
                   └── Forge Storage
```

The frontend and resolver are components of the same application, not separate products or independently hosted services.

## 4. Repository Structure

The initial application structure is:

```text
manifest.yml
package.json
src/
├── index.ts
└── definitions.ts
static/
└── app/
    ├── index.html
    ├── vite.config.ts
    └── src/
        ├── main.tsx
        ├── App.tsx
        └── styles.css
```

Responsibilities:

- `manifest.yml` declares the Jira module, resources, runtime, and resolver entry point.
- `src/index.ts` exports the Forge resolver handler.
- `src/definitions.ts` defines shared resolver types.
- `static/app/` contains the React frontend.
- Vite builds the frontend into `static/app/dist`.

The structure may evolve as features are implemented.

Avoid creating unnecessary layers or abstractions before they are justified.

## 5. Frontend Responsibilities

The React frontend handles:

- Displaying Jira issue context.
- Preparing user-facing inspection requests.
- Copying Markdown to the clipboard.
- Downloading inspection packages.
- Selecting and importing JSON files.
- Displaying flexible investigation nodes and execution relationships.
- Handling diagram interactions and optional relative-impact highlighting.
- Presenting validation errors and findings.

The frontend may use supported Forge Bridge APIs to access Jira context and permitted Jira REST operations.

Secrets and authoritative storage operations must not be exposed to the browser.

## 6. Forge Resolver Responsibilities

The resolver handles application operations that require trusted execution.

Responsibilities include:

- Validating imported analysis data.
- Enforcing import and naming rules.
- Reading and writing saved flows.
- Deleting individual flows.
- Associating flows with Jira issues.
- Returning normalized data to the frontend.

The resolver should contain business logic that must remain consistent regardless of frontend behavior.

Shared contracts should be typed.

## 7. Jira Integration

FlowLens uses Jira issue context to identify the current issue.

The resolver identifies the issue using trusted Forge context and reads Jira REST v3 as the current user.

The inspection request may contain relevant fields such as:

- Issue key and title.
- Description.
- Issue type.
- Priority and status.
- A visible, unambiguous Acceptance Criteria custom field when the issue supplies a value.
- Attachment metadata and content when requested and permitted.

The manifest declares `read:jira-work` for Jira REST reads and `storage:app` for Forge storage.

## 8. Inspection Export

The application supports two export modes.

### Copy Inspection Prompt

Generates structured Markdown and copies it to the clipboard.

Attachments are excluded.

### Export Inspection Package

Generates a downloadable package containing the inspection instructions, issue context, and accessible attachments.

A per-file and total size limit bound downloads. The package manifest records exclusions and failures. See [Inspection Template](implementation/INSPECTION_TEMPLATE.md).

The package must preserve useful evidence.

Both export modes must use the same core inspection instructions.

## 9. Analysis Import

The user selects a JSON file generated by an external AI assistant.

The browser checks the file and request size, then sends the JSON text to the resolver. The resolver verifies Jira issue access, validates the version and references, assigns independent flow identities, and commits the graphs and an updated issue directory together. The panel shows the new list after confirmation.

### Additive Import Rule

**Every import adds new flows. Existing flows are preserved.**

Importing a flow with an existing name must not replace the existing flow.

### Duplicate Name Rule

Names must be unique within a Jira issue.

For example:

```text
Payment Processing
Payment Processing (0)
Payment Processing (1)
Payment Processing (2)
```

When a name already exists, append the next available incremental suffix, starting at `(0)`.

Duplicate names within the same import must also be resolved.

The resolver allocates names against the current issue directory inside a revision-checked transaction.

Concurrent imports must not produce duplicate names.

### Identity Rule

Imported flow IDs identify flows within the analysis file.

Persisted flows must receive identities that do not collide with previously saved flows.

Display names and persistent identities are separate concepts.

Optional references such as `basedOnFlowId` must be preserved or remapped appropriately when importing multiple related flows.

## 10. Storage

The Forge Custom Entity Store holds an issue directory and separate graph records. Installation isolation is enforced by Forge. Keys also use the trusted cloud ID and stable Jira issue ID. The panel retrieves the directory at startup and opens graph records individually.

One custom instruction belongs to the authenticated account within the Jira site. Both the issue directory and preference records use revision checks for simultaneous edits. See [Data Storage](implementation/DATA_STORAGE.md) for ownership, limits and transaction behavior.

## 11. Validation and Security

Imported JSON is untrusted input.

The application must validate structure, supported values, references, and reasonable size limits before persistence.

Source-code snippets, descriptions, and AI-generated findings must be treated as data, not executable instructions.

The UI must render imported content safely.

Access to saved analysis must respect the relevant Jira and Forge authorization boundaries.

Storage operations must not rely solely on issue identifiers supplied by an untrusted frontend.

## 12. Error Handling

Errors should be understandable and actionable.

Important failure categories include:

- Missing Jira context.
- Insufficient Jira permissions.
- Invalid JSON.
- Unsupported schema version.
- Invalid node or edge references.
- Oversized imports.
- Storage failures.
- Attachment retrieval failures.
- Resolver communication failures.

The application should preserve existing data when an import fails.

## 13. Architecture Principles

- Keep FlowLens as one Forge application.
- Prefer existing Forge capabilities over additional infrastructure.
- Keep application logic simple and cohesive.
- Reuse shared contracts and avoid duplicate validation rules.
- Separate presentation concerns from authoritative persistence operations.
- Preserve imported content and optional source evidence without assuming every node has a source reference.
- Avoid unnecessary abstractions.
- Keep implementation details documented without duplicating the product overview.

Architecture decisions may evolve independently of the product vision.
